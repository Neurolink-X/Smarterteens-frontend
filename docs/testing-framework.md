# SmarterTeens unified feature qualification framework
Applies to every change: learning, simulations, Future World, coaching SaaS, payments (when enabled), accounts, staff, parents, admin and infrastructure.

## Required checks
1. Feature context and roles: maintain qa/feature-contracts.json. Every app/lib/db source file is registered; changed feature implementations require a corresponding changed test file. This checks evidence presence, not test quality; reviewers must assess meaningful assertions and expand groups for new behavior.
2. Strict TypeScript, unit and calculation tests, production build, real HTTP smoke tests, request validation, security headers and private cache contracts.
3. Chromium desktop and mobile browser tests against the actual production-mode Next server: route rendering, horizontal overflow, uncaught runtime/console errors, navigation, search, local persistence, real diagnostic requests, simulation consistency, pricing/educator tools and regression. Browser emulation is not physical-device certification.
4. Protected isolated staging: real browser login with two different verified owners, tenant API and direct Supabase user-token RLS attempts; synthetic admissions, status updates, batches, learner codes, attendance, invoices and receipts. Never use real learners or production data. No fake auth, service-role bypass, or secret-bearing artifacts.
5. Aggregate smarterteens-release-gate rejects failure, cancellation or skip. GitHub branch protection must require this exact check on main and require up-to-date branches; prohibit bypass, direct pushes and force pushes. Enable the same on master until it is retired. Connector cannot change repository rulesets; settings must be applied by an authorized repository administrator.
6. Vercel buildCommand checks exact production Git SHA against successful push CI, then runs the code-level qualification. It fails closed on unknown SHA, wrong branch or pending/failed CI. Git-triggered production builds may start before CI completes; redeploy only that approved SHA after CI success. Configure Vercel Deployment Checks to require smarterteens-release-gate before assigning production domains; never force promote. No paid feature is assumed.
7. A failure must produce a fix and rerun at the new commit, not disable a test or auto-merge. CI automatically runs on subsequent PR pushes. It cannot write reliable fixes itself. No autonomous code rewriting or paid runner configured.

## Authenticated CI staging (automatic)
Each hosted GitHub runner starts a disposable local Supabase stack with pinned CLI 2.122.1, applies the same SQL migrations, creates two verified synthetic users through real Auth, and creates separate institutes through their own user tokens. No cloud project, static credentials, or GitHub environment secrets are needed. The exact loopback origin and staging marker are required. The application rejects loopback in Vercel. The privileged local fixture key is never passed to the application or browser. The stack is stopped without backup after the test. Hosted production credentials are never used. This is real integration testing in an isolated CI environment, not deployed-cloud staging verification. Before public release also verify actual hosted deployment/API connectivity, without synthetic mutations on production. A separate hosted staging project may be used for additional cloud parity tests when available.

## Role coverage
Visitor/student: public local learning; parent: student-controlled printed evidence only; teacher: public question bank. Verified coaching owner: own tenant only. Authenticated students, teacher, guardian, finance, institute admin, platform admin and support roles are not implemented yet. Each future role must add allowed and denied cases, actual authenticated role-specific E2E, database RLS and privilege escalation tests before release. Do not claim role isolation for nonexistent accounts.

## Performance & safety
Local CI health p95 budget 1.5 seconds (not a production SLA); diagnostic request count and slider local-only behavior are checked. Add representative authenticated latency/load, caching, database query counts, browser Web Vitals (LCP/INP/CLS), accessibility and physical-device testing before scale. Educational safety/content review is required in addition to automated correctness. No synthetic student data may be represented as real platform outcomes.
